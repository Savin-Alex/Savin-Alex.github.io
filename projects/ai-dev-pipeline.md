**2026 · Соло-проект для портфолио · Рабочий локальный прототип**

Процесс из трёх AI-агентов — планировщика, разработчика и ревьюера — проводит небольшую задачу из Jira до pull request в GitHub с обязательными проверками кода и ревью человеком.

## Задача

При генерации кода с помощью AI разработчик обычно вставляет задачу, получает код и проверяет его вручную. Такой сценарий не заменяет процесс поставки: нет приёма задачи, ревью, прослеживаемости и ответственности человека. Кроме того, сгенерированный код может быть небезопасным.

## Мой вклад

**IT Project Manager в соло-проекте: отвечал за цель, план и результат, реализовал прототип.**

- Определил цель, границы проекта и критерии готовности, подготовил реестр рисков и план отката.
- Спроектировал процесс от задачи в Jira до pull request с двумя режимами: пробный прогон без изменений и контролируемый реальный прогон.
- Разработал агентов на Claude API и связал их с Jira и GitHub.
- Ввёл обязательные проверки: тесты в Docker-контейнере без доступа к сети, поиск секретов в коде, ревью человеком и лимит расходов на API.

## Что реализовано

<ol class="project-flow">
  <li><strong>Задача из Jira</strong><span>Пайплайн берёт задачу с критериями приёмки и переводит её в работу.</span></li>
  <li><strong>План и код</strong><span>Планировщик составляет план, разработчик пишет код и тесты.</span></li>
  <li><strong>Проверки</strong><span>Поиск секретов, тесты в изолированном контейнере и ревью. Ревьюер может вернуть код на доработку.</span></li>
  <li><strong>Pull request</strong><span>После одобрения создаётся pull request, статус задачи в Jira обновляется. Слияние выполняет человек.</span></li>
</ol>

## Результат

**Рабочий прототип: путь от задачи в Jira до pull request работает на реальных Jira и GitHub, а проверки останавливают код с ошибками.**

- По двум задачам из Jira пайплайн создал pull request и обновил статус задач. Код в этих прогонах готовил встроенный шаблон, а не языковая модель.
- В прогоне с Claude тесты не прошли, и ревьюер указал причину — ошибку импорта. Ошибка осталась после повторной попытки, поэтому pull request не создавался. Прогон стоил около $0,01.
- По каждому прогону сохраняется отчёт: статусы этапов, результаты тестов, причина остановки и расходы.
- Большинство записанных прогонов выполнено без модели, поэтому долю успешных задач ещё предстоит измерить.

## Дальнейшее развитие

Следующий этап — запустить модель на реальных задачах и измерить, какая доля задач доходит до pull request, а также стоимость и время прогона. Затем — панель метрик и подтверждения по ролям (PM, техлид, безопасность).

<details markdown="1"><summary>Подробности: решения и риски</summary>

- В режиме контроля реальный прогон разрешён только в GitHub Actions после подтверждения; по умолчанию выполняется пробный прогон.
- Лимит расходов останавливает прогон, если затраты на модель превышают бюджет.
